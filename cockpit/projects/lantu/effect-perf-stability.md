## 1. 效果指标

### 1.1 评测方法与工具

#### 1.1.1 评测方式对比

| 评测方式           | 适用场景               | 优势说明                                                                                            |
| :----------------- | :--------------------- | :-------------------------------------------------------------------------------------------------- |
| **SDK 方式** | 算法快速验证阶段       | 便于直接读取本地 JSON 数据文件进行批量推理，快速验证模型效果与性能基线。                            |
| **APK 方式** | 完整业务链路与平台对接 | 集成 AADK 框架，通过 JNI 调用推理服务；与“元启”平台通过 HTTP 对接，便于自动化统计分析与云端评测。 |

#### 1.1.2 日志提取命令

用于从运行日志中快速过滤出预处理耗时、推理耗时、最终结果等关键信息：

```bash
grep -E "image path:|PERF: ModelRunner::inference|final result|final reply|aadk.*: preprocess time" 0529-1741.log > 0529-1741grep.log
```

> [!WARNING]
> **这条 grep 有两处 pattern 与当前分支日志串对不上（已对 `lantu_sdk_dev` + agent_group 核实）**
>
> - **`final reply` 抓不到**：`final result` 在 agent_group dispatcher 中真实存在（`[AADK] … final result`，如 `outcar_qa_dispatcher.cpp` / `incar_item_detect_dispatcher.cpp` / `dress_detect_dispatcher.cpp`），但 **`final reply` 在 aadkcore 与 agent_group 的自有源码中均无匹配**（只在第三方头文件里有噪声）→ 疑为旧日志串，建议移除或核实其来源分支。
> - **`aadk.*: preprocess time` 只抓得到 LLM 侧、抓不到图像/VIT 侧**：代码里有**两条**预处理计时——LLM 侧 `preprocess time: {} ms`（`qnn_model.cpp:731`，prompt 构建 + LoRA/prefix 设置）与图像/VIT 侧 `image preprocess time: {} ms`（`qnn_model.cpp:496/547`，含 resize + VIT encode）。该 pattern 的 `: preprocess time` 冒号锚点**匹配不到** `image preprocess time`（"preprocess" 前多了 "image "），故当前命令**漏掉了 VIT/图像预处理耗时**——而这正是把 TTFT 拆成「VIT」与「LLM prefill」两段所必需的（见 §2.1 TTFT 口径核实）。另注意 pattern 用小写 `aadk`，而日志 tag 为 `[AADK]`，`grep -E` 默认大小写敏感，需确认实际日志大小写或加 `-i`。
> - **建议改为**（同时抓两段预处理 + 首 token 时刻，便于分离 VIT 与 prefill）：
>
> ```bash
> grep -iE "image path:|PERF: ModelRunner::inference|final result|image preprocess time|preprocess time:|first_token_time|ttft:" 0529-1741.log > 0529-1741grep.log
> ```

> 评测自动化待补：上述 grep 可封装为脚本，自动解析 log 输出 TTFT/TPS 的均值与方差（含 p50/p95/p99），减少手工统计误差。**脚本须同时解析 `image preprocess time` 与 `PERF: … ttft`**，才能把 TTFT 分解为「图像/VIT」与「LLM prefill」两段（否则 §2.1 的 TTFT 口径无法验证、§2.2 的量级互核也无法做）。

### 1.3 舱内业务效果指标

> 数据来源：**0817 测试报告**（最近一份含舱内效果的报告；0828 版仅测舱外）。遗留检测的准确率/召回率按报告混淆矩阵核算：准确率=(TP+TN)/(TP+TN+FP+FN)，召回率=TP/(TP+FN)。
>
> **指标口径说明**：舱内实际采用 **Accuracy / Recall** 与**分级通过率**两类指标。原篇标题所列 **F1 / mAP 未在本批评测中计算**，属**待补**（如需 F1 可由现有混淆矩阵推出；mAP 仅当有检测框/排序结果时才适用）。

| 业务场景         | 评估指标          | 测试结果                                              | 目标基线              | 备注                                       |
| :--------------- | :---------------- | :---------------------------------------------------- | :-------------------- | :----------------------------------------- |
| **舱内遗留儿童** | Accuracy / Recall | 准确率 **97.7%**、召回率 **95.4%**（整体 487 样本，TP228/TN248/FP0/FN11） | ACC≥90%、召回优先 | 涉及安全，需极高召回率；0817 报告 4.2 |

| **舱内衣着识别** | 分级通过率        | 无衰减档：颈部 **96.5%**(410/425)、手臂 **100%**(441/441)、上衣厚度 **99.1%**(439/443) | 无衰减≥90% | 0817 报告 4.1 舱内空调；含 -10/-20/-30pp 衰减档 |

> [!WARNING]
> **遗留儿童召回 95.4% 的安全差距（不得轻描淡写）**
>
> 遗留儿童是**安全相关功能**。召回率 95.4% 意味着 FN=11 / 239 个正样本被漏检，**约每 22 个遗留儿童漏检 1 个**（漏检率 ≈ 4.6%）。这与「需极高召回率」的安全目标存在**明确差距**——对儿童遗留这类场景，业界通常要求召回逼近 99%+，95.4% 不足以支撑「安全」宣称。
>
> 从混淆矩阵看 **FP=0 且 FN=11**：零误报但漏检 11 例，说明判定**阈值偏保守**（倾向避免误报），而这对「召回优先」的安全功能恰是**反方向**——应评估在不显著抬高误报率的前提下把阈值向召回侧倾斜。
>
> **建议**：① 明确遗留儿童的目标召回红线（如 ≥99%）并给出差距；② 分析 11 例 FN 的共性（光照/遮挡/姿态/年龄）；③ 该功能的功能安全论证（ISO 26262 / ASIL、失效降级策略）目前各篇均未覆盖，属整体缺口，参见 [运维及安全篇 §4](ops-security.html)（该篇已按「量产应有形态」补出功能安全框架，均为设计目标、未落地）。

> **小样本格子的「通过/不通过」判定证据不足（样本量与判定口径双缺口）**

>
> **② 小样本格子不足以支撑判定**（Wilson 95% CI，推导）：
>
> | 格子 | n | 点估计 | 95% CI（约） | 判定可靠性 |
> | :--- | :--- | :--- | :--- | :--- |
> | 交通标识-禁止（0828） | 2 | 100% | [34%, 100%] | 无意义 |
> | 交通标识-指示&警告（0828） | 3 | 100% | [21%, 100%] | 无意义 |
> | 4 类交通标识 | 13 | 92.31% | [66.7%, 98.6%] | 不稳健 |
> | 动物泛化 | 7 | 57.14% | [25%, 84%] | 证据弱 |
>
> 0828 的交通标识核心样本量较 0817 **骤降**（禁止 11→2、指示&警告 5→3），该两行 0828 的 100% **不代表能力保持，只代表测得少**。
>
> **③ 建议**：设**最小样本量门槛**——若要求通过率 95% CI 半宽 ≤ 5pp，在 p≈0.9 时需 **n ≈ z²p(1−p)/0.05² ≈ 138**（±3pp 需 ~384）；现有 n=2~13 的格子差 1~2 个数量级。故核心类别每档 **n 应 ≥ ~140** 才能支撑阈值判定，**n<30 的格子只记录、不判定**；并明确「通过」用点估计还是 CI 下界口径（安全相关场景如遗留儿童建议用 CI 下界）。

## 2. 性能指标

### 2.1 速度计算维度定义

| 性能指标               | 英文缩写 | 含义说明            | 计算起点/终点                                               |
| :--------------------- | :------- | :------------------ | :---------------------------------------------------------- |
| **首字延迟**     | TTFT     | Time To First Token | 从输入图像/Prompt处理完毕到输出第一个Token的耗时            |
| **生成速度**     | TPS      | Tokens Per Second   | Decode 阶段每秒生成的 Token 数量                            |
| **端到端总耗时** | Total    | 整体流程耗时        | 包含预处理 + VIT encode + LLM prefill + LLM decode + 后处理 |

> [!NOTE]
> **TTFT / TPS 的代码级口径（已对 `lantu_sdk_dev` 核实）——与「仅含 LLM prefill」的说法不符，待核实**
>
> 本篇 TTFT / TPS / output_tokens 是 **genai 运行时返回的 `ModelResponse` 字段**，不是评测脚本事后计算的：`qnn_model.cpp` 计算后由 `model_runner.cpp` 打印 `PERF: ModelRunner::inference leave tps: {}, ttft: {}, output_tokens: {}`——§1.1.2 的 grep 正是抓这条日志。代码级定义：
>
> - **TTFT = `first_token_time − start_time`**（`qnn_model.cpp:759-762`）。`start_time` 在 `streamGenerate` 入口、`buildLlmsPrompt` **之前**取值，而 `buildLlmsPrompt` 内部会调 `preprocessImage` → **VIT encode**（`qnn_model.cpp:982/991`）。因此 **TTFT 实际包含：图像预处理 + VIT encode + prompt 构建 / LoRA / prefix 设置 + LLM prefill + 首个 decode token**。
> - **这与 §2.2 口径说明①「TTFT 为 0601 之后口径（仅含 LLM prefill，不含图像处理）」相矛盾**，也与本表「从输入图像/Prompt 处理完毕到第一个 Token」的表述不一致（后者暗示图像已处理完）。两种可能：① 0902 数据用的不是 SDK `response.ttft` 字段、而是 harness 另算的口径；② 0601 前后代码/口径变过。**需向测试同学确认 0902 表的 TTFT 到底取的是哪个口径**——这直接决定 §2.2 的 TTFT 量级互核与「VIT 是否计入 TTFT」的结论。
> - **TPS = `output_tokens ÷ (end_time − first_token_time)`**（`qnn_model.cpp:800-806`）：即**纯 decode 段**（从首 token 到末 token）、**不含 TTFT**，`output_tokens` 含首 token。故 `Total ≈ TTFT + output_tokens/TPS + 后处理/调度开销`——其中**图像预处理与 VIT encode 已并入 TTFT**（不再单列），残差项只剩后处理与阶段间调度。
>
> **推论**：若 TTFT 含 VIT，则「TTFT 随 VIT 档位（视觉 token 数）显著变化」是预期内的（见 §2.2 量级互核）；要把 VIT 从 TTFT 里分离，需同时抓 `image preprocess time`（VIT/图像段）与 `PERF: … ttft`（见 §1.1.2 的修正 grep）。

> [!NOTE]
> **TTFT / TPS 的量级互核与口径陷阱（推导，非实测归因）**
>
> **① TTFT 与视觉 token 数高度一致（支持「TTFT 由 VIT 档位主导」）**。用 [架构篇 §7.3](genai-architecture.html) 的视觉 token 推导（小档 448×448 ≈ 196 token/帧、大档 1024×768 ≈ 768 token/帧）对各场景 TTFT 做「隐含吞吐 = 视觉 token ÷ TTFT」检查：
>
> | 场景/阶段 | VIT 档位 | 视觉 token（推导） | TTFT (ms) | 隐含吞吐 (token/s) |
> | :--- | :--- | :--- | :--- | :--- |
> | 舱内衣着 | 小档 | ~196 | 165.5 | ~1184 |
> | 舱外 stage1 | 大档 | ~768 | 548.4 | ~1401 |
> | 舱内遗留物 | 大档 | ~768 | 512.1 | ~1499 |
> | 舱内遗留儿童 | **待澄清** | ~768（若大档） | 480.8 | ~1597 |
>
> 四个场景的隐含吞吐落在 **1184~1597 token/s 的窄带内（极差仅 ~1.35×）**，与「TTFT ∝ 视觉 token 数」的模型一致 → **2.2 的 TTFT 数据量级自洽、物理可信**。（若进一步把 TTFT 近似为 LLM prefill，按 `有效算力 ≈ 2N×吞吐`、N≈4B 折算为 ~9.5~12.8 TFLOPS、对 ~35 TFLOPS FP16 峰值的 MFU ≈ 0.27~0.37，落在 prefill 典型 0.2~0.4 区间；但 §2.1 已指出 TTFT 实含 VIT encode，故该 MFU 折算仅作量级参考，严格互核需先分离 VIT 与 prefill 两段计时。）对照 [AIService 篇 §6.2](aiservice-integration.html) 的「字数→prefill」表按「字数≈token」折算出 ~2400~3700 token/s、MFU 0.5~0.9（该篇已自标存疑）——本篇按视觉 token 折算明显更落在合理区间，**侧面支持「中文经 Qwen tokenizer <1 token/字、字数会高估 token 数」的判断**。
>
> **② 遗留儿童大概率走大档（由 TTFT 反推，非配置核实）**：若遗留儿童走小档（196 token），隐含吞吐仅 196/0.4808 ≈ **408 token/s**，比其它场景低 3~4 倍、明显离群；走大档（768）则 ~1597 token/s、与其它场景同带。故推断**遗留儿童也走大档**——但 [架构篇 §3.2](genai-architecture.html) 的档位表未列遗留儿童，属**待澄清**（需对 dispatcher 的 `resized_width/height` 核实）。
>
> **③ TPS 的阶段差异不能归因到约束解码（口径陷阱）**：stage1/2/3 的 TPS 为 72.1 / 80.6 / 95.1，方向上与「stage1/2 开约束解码、stage3 不开」一致；但**未控制上下文长度**——stage3 的上下文最长（含 stage1/2 输出的结构化拼接），按理 decode 应更慢，却 TPS 最高。故 TPS 的阶段差异**混杂了约束解码开销、上下文长度、输出长度**，不能据此断言「约束解码拖慢 ~X%」。要归因需**同上下文 A/B**（带/不带 grammar 各跑一轮，方法见 [AIService 篇 §6.2](aiservice-integration.html) 的 grammar A/B）。

> [!WARNING]
> **跨篇对账：genai 端到端绝对值不可跨篇直接比**
>
> [GenAI vs AIService 篇 §2](genai-vs-aiservice.html) 的 genai 侧为 **2026-09-16** 实测（按 0915 调整**应为 4 核 NPU**、统计字段 `infer_total`、场景集不同）：车辆 2675 / 植物 2364 / 交通 2509 / 动物 1559 / 通用 2063 ms。与本表（09-02、3 核、字段 `Total`）的车辆 1978 / 植物 1994 / 交通 2001 / 动物 1770 / 通识 1964 ms 相比，差异为 **+35% / +18% / +25% / −12% / +5%，方向不一致**，且 09-16 按 0915 调整应已是 4 核、反而整体更慢。两次测量的**日期、NPU 核数（3 vs 4）、场景集、测量 harness、统计字段**（`Total` 与 `infer_total` 是否同义**待澄清**）均不同，因此 genai 绝对时延**不能跨篇直接对比或互相对账**，只能在各自口径内使用。
>
> **连相对排序也不稳定**：本表（09-02）舱外由慢到快为 交通 2001 > 植物 1994 > 车辆 1978 > 通识 1964 > 动物 1770；09-16 那批为 车辆 2675 > 交通 2509 > 植物 2364 > 通用 2063 > 动物 1559。两批**唯一稳定的共同点只有「动物最快」**，其余排序随批次变化 → 进一步说明绝对值与排序都不可跨篇复用，跨篇只能各用各的口径。

> [!NOTE]
> **全流程 TTFT/TPS 聚合口径（严谨性修正）**
>
> 原篇「全流程」行填 TTFT **353.5** / TPS **80.8**，并在脚注称其为「各阶段均值」。但按三阶段简单均值实算：TTFT=(548.4+288.6+145.3)/3=**327.4**、TPS=(72.1+80.6+95.1)/3=**82.6**，与 353.5/80.8 **均不相符**；用 token 加权等其它口径也无法从所给阶段值复现。因此 353.5/80.8 的**聚合口径无法从现有材料复现**（是逐请求总 TTFT 均值？token 加权？），标注**待澄清**。
>
> 本表为保持自洽，统一改用**可复现的各阶段简单均值 327.4 / 82.6**；原 353.5/80.8 予以保留记录、不再作为结论依据。若后续拿到逐请求原始数据，应明确「全流程 TTFT」的确切定义（建议定义为：逐请求端到端首字延迟的均值）并重算。
>
> **但 327.4 与 353.5 都不是「用户可感知的首字延迟」（更重要的口径问题）**：舱外是**串行三阶段流水线**，对多个顺序阶段的 TTFT 取平均**没有物理意义**——用户看到的首个字来自 **stage1 的流式输出**，故用户可感知的端到端首字延迟 ≈ 图像预处理 + VIT + **stage1 TTFT（≥548.4ms）**，而非 327.4ms。建议把该行拆成两个指标：**「首阶段 TTFT（用户可感知首字）」**与**「阶段 TTFT 均值（仅作阶段级参考）」**，避免把 327.4 误读成端到端首字延迟。
>
> **同一行三列的聚合口径互不相同，不可横向代入公式**：该行 TTFT/TPS 是「阶段均值的均值」、Output-tokens **104** 是「逐请求总输出的均值」（≈ 阶段和 107.1）、Total ~1942 是「逐请求端到端的均值」。因此 **`104 ÷ 82.6 ≈ 1259ms` 不等于该行的 decode 时间**（82.6 是阶段均值口径、104 是逐请求总输出口径，分母分子不同源），§2.2 下方「Total 对账」NOTE 已据此说明缺口属口径差。

> [!NOTE]
> **Total ~1942ms 与阶段值相加对不上（~300ms 缺口是聚合口径差，不是算错）**
>
> 把三阶段值直接相加：ΣTTFT = 548.4+288.6+145.3 = **982.3ms**，Σdecode（各阶段 output tokens ÷ 各阶段 TPS：382.8+511.2+402.7）≈ **1296.7ms**（若按全流程 104 tokens ÷ 均值 TPS 82.6 口径则 ≈ 1259.1ms），合计 **≈2241~2279ms**，比全流程 Total ~1942ms 高约 **300ms**。根因是两者**聚合口径不同、分母不同**：
>
> - **阶段行**是对「**仅执行了该阶段的请求**」求均值——舱外多为 3 阶段，但 bbox 为空时跳过裁剪走 2 阶段，并非每个请求都执行全部三个阶段；
> - **Total 行**是对「**全部请求（含 2 阶段请求）**」求均值——2 阶段请求路径更短，把整体均值拉低。
>
> 因此**阶段值不可相加重构 Total**，该 ~300ms 缺口属口径差异而非数据错误。**2 阶段请求占全量的比例**在现有材料中未单列 → **待澄清**（需逐请求原始数据才能算出）。同理，全流程 Output-tokens **104** 与阶段和 27.6+41.2+38.3=**107.1** 也是分母口径之差；104 是全部请求的实测平均总输出还是取整值，**待澄清**。
>
> **把「2 阶段占比」从待澄清收紧为一个可检验的下界（推导）**：设 2 阶段请求占比为 p，则 `Total均值 ≈ p×T₂ + (1−p)×T₃ + W`，其中 T₃ = 三阶段 (TTFT+decode) 之和 ≈ **2279ms**、T₂ = 跳过 stage2 后的两阶段之和 = 548.4+382.8+145.3+402.7 ≈ **1479ms**、W = 阶段值未含的「后处理 + 阶段间调度/LoRA 切换」开销（≥0；**图像预处理与 VIT encode 已计入各阶段 TTFT，见 §2.1，故不在 W 内**）。代入 Total ~1942：`p = (2279 − 1942 + W) / (2279 − 1479) = (337 + W) / 800`。
> - 即使 **W=0**，也需 **p ≥ 42%** 才能让 Total 与阶段值自洽；W 为后处理+调度，量级应较小（几十~百 ms），故 p 大致落在 **~42%~55%**。
> - 若被跳过的不是 stage2 而是 stage3（T₂ ≈ 1731ms），则 p ≈ **62%**（W=0 时）。
> - **可证伪检验点**：拿到逐请求数据后先核 p 是否落在此区间——若明显偏离（如 p<20% 或 >80%），则说明 Total 与阶段值**根本不同源**（不是同一批请求/同一口径），而非单纯的 2 阶段占比问题。
>
> **舱内 2 阶段场景的残差方向与舱外相反（更深的口径矛盾，待澄清）**：对舱内两行按「TTFT + output_tokens/TPS」重构：
> - 遗留儿童：480.8 + 25.7/62.8×1000 = 480.8 + 409.2 = **890.0ms**，Total 1506.8 → 残差 **+616.8ms**（Total 比阶段和大）；
> - 遗留物：512.1 + 17.3/58.3×1000 = 512.1 + 296.7 = **808.8ms**，Total 1490.3 → 残差 **+681.5ms**。
>
> 舱内是**正残差**（Total > 阶段和，+617~+682ms），舱外却是**负残差**（Total < 阶段和，−337ms）。**两者方向相反，不能用同一套口径解释。** 注意：§2.1 已确认 VIT/预处理计入 TTFT，故舱内这 +617~+682ms **不能**用「Total 还含 VIT/预处理」解释——它要么是后处理 + 两次推理间的调度/LoRA 切换（但 ~600ms 量级偏大、可疑），要么说明舱内 2 阶段行的 TTFT/tokens 填的是**均值而非求和**（见下）。一个可能的化解：若舱内「全流程（2 阶段）」行的 TTFT/tokens 填的是**两阶段均值**（而非两阶段之和，与舱外全流程行改用简单均值的口径一致），则遗留儿童重构为 961.6+818.5=1780.1、残差 **−273ms**，遗留物为 1024.2+593.5=1617.7、残差 **−127ms**——**与舱外同为负、方向一致**，可用同一「口径差」解释。
>
> → **待澄清（关键）**：舱内 2 阶段行的 TTFT / Output-tokens 到底是「两阶段之和」还是「两阶段均值」？这决定残差是 +617~+682ms 还是 −127~−273ms，也决定舱内/舱外能否用同一口径对账。现有材料未注明，需逐请求原始数据或测试同学确认。

### 2.3 时延分布与冷启动（待补）

现有时延均为**均值**，缺少分布与启动态数据，以下待补：

- **时延分位数 p50 / p95 / p99**：座舱交互体验由长尾（p95/p99）决定，仅均值不足以评估。需从逐请求原始数据重算（建议随 1.1.2 的评测脚本一并产出）。
- **冷启动 vs 稳态**：模型加载后首次推理（含 prefix cache 冷启动）与稳态推理的时延差异未测，需区分「首次 TTFT」与「稳态 TTFT」。

### 3.2 多核优化（单核 → 3 核）

| 测试维度         | 3 核模型    | 单核模型    | 备注                       |
| :--------------- | :---------- | :---------- | :------------------------- |
| **舱外端到端耗时** | `3806 ms` | `6559 ms` | 算术降幅约 42%，但**出处存疑** |

> [!WARNING]
> **出处存疑，撤回「已验证」定性**：`3806 / 6559 ms` 的来源在原篇中即为「疑为 0425 实车摸底或单核内部对比」，其逐阶段 TTFT/TPS/tokens 明细在现有材料中**未覆盖**；单核为 4 月前配置（readme：4 月起统一三核），**无对应报告**。降幅 (6559-3806)/6559≈42% 算术上成立，但因**数据源无法坐实**，本条**不作为已验证结论**，需补单核/三核的同口径对照报告后方可确认。

> **两条新增的内部矛盾（本轮深挖发现，进一步削弱本条）**：
>
> 1. **3806 疑为「舱内遗留儿童」值被误当「舱外端到端」引用**：3.6 的 0428 早期基线里 **left_child = 3810ms**，与本条的「3 核舱外端到端 **3806ms**」仅差 4ms（0.1%）；而 0428 的**舱外**各场景为 car 5770 / animals 5965 / plant 5434 / traffic_sign 5548，与 3806 差 30~40%。这强烈提示 3806 可能是把 0428 的**舱内遗留儿童**值误标成了「舱外端到端 3 核」。若属实，则 −42% 不仅出处存疑，还**场景张冠李戴（舱内 vs 舱外）**。需向数据源核实 3806 的确切场景与日期。
> 2. **与唯一有出处的 3 核早期数据对不上**：若按 3.6 认定 3806 是「旧模型」，则 6559（单核）也必须是同一旧模型才可比；但现有材料里**唯一有出处的 3 核早期数据**（0428：舱外 5434~5965ms）与 3806 差 30~40%，两者不可能同为「3 核旧模型舱外端到端」。
>
> → 综合以上，本条证据状态从「出处存疑」**进一步降级**：在拿到「同一模型、同一场景、仅核数不同」的对照前，多核（单核→3核）收益**与 3→4 核一样，实际无任何可用数据**，同属待补。

### 3.3 Prefix cache（部分实测 + 部分待补）

- 定性：复用系统提示词/前缀 KV，减少重复 prefill 计算。11 个 prefix 的 system_prompt 经 tokenizer 实测为 **318~959 tokens、均值 ~610**（详见 [架构篇 §7.3](genai-architecture.html)）。
- **已有实测（aiservice 形态，端到端 A/B）**：[AIService 篇 §6.2](aiservice-integration.html) 给出 08-11 prefix 全开 vs 08-07 的端到端提速——**Agent300 −7.9% / Agent200 −10.8% / Agent100 −0.1%**（新增 prefix 的 step2 −2.2%）。这是目前唯一的 prefix cache 量化收益数据。
- **收益为何因场景差一个数量级（机理，已对架构篇核实）**：前缀缓存**只省 system_prompt 那段文本 prefill，视觉 token 每帧都要重算、不被文本前缀覆盖**。故**视觉 token 占比越高、prefix 收益越低**：
  - Agent100（舱内遗留物）走**大档**（~768 视觉 token/帧）> 其 prefix（cnyb-left 486）→ 文本前缀覆盖不到一半 prefill，端到端仅 **−0.1%**；
  - Agent200（衣着）走**小档**（~196 视觉 token）< 其 prefix（cnyb-cloth 959）→ prefix 占 prefill 大头，端到端达 **−10.8%**。
- **该 A/B 的口径限制（不可当作纯 prefix 收益）**：① 是 **aiservice 形态**的端到端值，非 genai 形态、也非 prefill 单项；② 08-11 与 08-07 之间**除 prefix 全开外还有前缀缓存路径修复等改动**，非严格控制变量；③ 端到端值还混杂 decode/HTTP/调度，prefix 只影响 prefill 段。
- **仍待补**：genai 形态的 prefill 级收益、命中/未命中的 **TTFT 差**（同请求带/不带 `prefix_cache_path` 的 A/B）、各场景**命中率**。建议评测脚本同时抓 `image preprocess time` 与 `PERF: … ttft`（见 §1.1.2），即可把 prefix 收益从 TTFT 里分离出来。

### 3.4 多 VIT（定量待补，但「档位 → 视觉 token → TTFT」机理链已可互核）

- 定性：按业务分档的多分辨率 VIT 输入（qwen3-omni-4b 定制；详见 [GenAI 架构篇 §3.2](genai-architecture.html)）。**档位路由精确口径（对齐架构篇，勿简化为「舱内小档/舱外大档」）**：
  - 舱内**衣着**（dress_detect）→ 小档 448×448；
  - 舱内**遗留物**（incar_item_detect）→ **大档 1024×768**（非小档）；
  - 舱外问答 **stage1** → 大档；**stage2** 视 `Stage2ImageMode`：`USE_FULL_1024`→大档、`USE_CROP_448`/`USE_FULL_448`→小档；
  - **遗留儿童**：架构篇档位表未列，**待澄清**（§2.2 的 TTFT 反推提示大概率大档）；
  - 非两档尺寸会**静默 fallback 到 448 小档**（`qnn_model.cpp` `get_vit_shape`），排查「尺寸不对却仍出结果」时留意。
- **机理链（可互核，非量化收益）**：小档 ~196 / 大档 ~768 视觉 token/帧（差 ~3.9×），视觉 token 主导 prefill/TTFT → 这正是 §2.2 中衣着 TTFT（165.5ms，小档）远低于遗留物/舱外 stage1（512/548ms，大档）的主因，也是 §3.3 prefix cache 收益因场景而异的根因。
- **定量待补**：相对单 VIT / 单一分辨率省多少计算或提升多少效果，无对照数据；建议补「同图走大档 vs 小档」的 TTFT/效果 A/B（档位由 dispatcher 写死的 `resized_width/height` 控制，可切换）。

### 3.5 INT4 量化（精度代价已有实测对照；时延收益待补）

- 定性：**W4A16**（权重 INT4、激活 FP16；VIT + LLM 均压权重，AIMET 制备）。注意「VIT 也压 INT4」的**激活位宽组合**（weight-only W4A16 还是 W4A8）架构篇未拿到模型团队明确口径，**以模型团队交付为准**（见 [架构篇 §5.2](genai-architecture.html)）。
- **精度代价已有实测对照（0527 build，云端浮点 vs 端侧量化，来源 `z_summary_0527`，见 [架构篇 §7.1](genai-architecture.html)）**：
  - 多数场景通过率差 **0~6pp**（nlg / 儿童遗留 / 遗留物近乎无损）；
  - **植物 caption 约 −10pp**；交通标识 bbox 小幅下降；
  - **衣着描述在 0527 版异常塌至 ~0%（浮点 51.76%）**，疑为该量化 build 的阶段性回归（可能与 VIT INT4 相关）。
  - **口径限制**：这是 **0527 build** 的浮点 vs 量化对照，非当前 build；且「衣着塌至 ~0%」是阶段性回归、后续版本待核。故它**坐实了「VIT INT4 有精度代价」这一方向**，但具体到当前模型的代价仍需以**当前 build 的 INT8 对照**重测。原「精度代价存疑待归因」据此**升级为「已有 0527 实测对照、当前 build 待复测」**。
- **时延收益待补（且机理上对 prefill/VIT 收益有限）**：INT4 相对 INT8/FP16 的时延与吞吐收益无测量数据。机理上 W4A16 主要**降内存占用 / 权重加载体积 / decode TPOT**（decode 是 memory-bound，压权重直接减每 token 读取字节）；但对 **compute-bound 的 prefill 与 VIT encode 基本无收益**（matmul 仍走 FP16 通路、峰值算力不变，dequant 反加开销，见 [架构篇 §5.2](genai-architecture.html) 与 [解码服务化 · TTFT 优化](../../general/infer-serving.html)）。故不应期待 INT4 改善 §2.2 的 TTFT，其收益应体现在 decode/TPS 与内存（§4.3）——**此为机理推导，实测仍待补**。
- **校准集披露（待补）**：AIMET INT4 的校准集构成（来源、规模、场景分布）与**是否与 banma 评测集重叠**，现有材料均未说明；若重叠，量化参数会对评测分布过拟合、分数虚高（校准集选择判据与重叠风险见 [调试与工具链篇 §2.1](../agent-framework/debug.html)）。

### 3.6 模型换代不作为优化收益（撤回 49%）

> [!WARNING]
> 原篇称「~1942ms 较早期 3806ms 再优化约 49%」。但 **3806ms 是旧模型**、**1942ms 是当前模型**，二者跨模型版本，49% 的差距**混杂了模型换代与工程优化**，无法归因于优化工作。本条**撤回「优化收益 49%」的结论**，仅陈述事实：当前模型舱外端到端 ~1942ms，早期旧模型为 3806ms，二者不可作为优化前后对比。

**早期基线（参考，非优化收益）**：上海 0428 首测（`性能测试报告v1.0_20260428-final.xlsx`，v0.1 早期模型、3 核测试台架、未加水冷）仅有**场景级整体耗时**，无逐阶段分解、无单核对照：car 5770 / animals 5965 / plant 5434 / traffic_sign 5548 / left_child 3810 ms（TTFT 1221~1674ms、TPS 47~54，均未达标）。此为**早期模型基线**，与当前模型不同版本，**不可用于计算优化收益**，仅作演进参考。

> [!WARNING]
> **0428 的 TTFT/TPS 是 0601 之前的旧口径，不可与当前 TTFT 直接比**
>
> §2.2 已注明当前 TTFT 为「0601 之后口径」，而 0428 的 TTFT 1221~1674ms 属 **0601 之前的旧口径**（很可能含图像处理/VIT，与当前口径定义不同）。因此**不能**说「TTFT 从 1221~1674ms 改善到 145~548ms、提升 3~8 倍」——两者口径不同，该比较不成立。**可比的只有端到端整体耗时**（0428 car 5770 → 0902 车辆 1978，同为端到端口径），但因跨模型版本，仍按本节原则**不作优化收益**、仅作演进参考。
>
> 另：0428 的 **left_child 3810ms** 与 §3.2 的「3 核舱外端到端 3806ms」仅差 4ms，疑为同一数值被误标场景，见 §3.2 WARNING 第 1 条。

### 4.3 内存占用分析

> **术语更正**：本节分析的是**内存（RAM）**，不是**存储（flash）**。原篇标题「存储占用分析」名不副实，已更正为「内存占用分析」。真正的存储占用（模型文件大小、`/AI` 分区、包体 378/222MB）是另一维度，见 [AIService 后端集成与重构](aiservice-integration.html)，本篇**待补**。
>
> **两个口径必须分开**：① **测试进程 CPU 侧 PSS**（`/proc/smaps`，本测试进程）；② **VmRSS + dma-buf**（进程常驻内存 + DSP/NPU 设备缓冲）。二者**不可互相比较**。

**① 测试进程 CPU 侧（genai 测试进程，2026-09-02 6h 连跑）**

| 指标                | 实测                | 说明                       |
| :------------------ | :------------------ | :------------------------- |
| Total PSS           | **~1.85 ~ 2.14 GB** | 6h 无单调增长（无泄漏迹象） |

**② 服务形态整机内存对比（aiservice vs genai，VmRSS + dma-buf）**

| 组成                             | aiservice   | genai       | 差异                       |
| :------------------------------- | :---------- | :---------- | :------------------------- |
| **VmRSS (CPU 进程)**       | 4613 MB     | ~2030 MB    | ai 高 2583 MB（~2.5 GB）   |
| ├ RssAnon（CPU 堆）        | ~3043 MB    | ~300~540 MB | **ai 高 ~2.5~2.7 GB（差异几乎全在此）** |
| └ RssFile（mmap 模型/LoRA/库） | ~1460 MB | ~1463 MB    | 基本相同（差 ~3 MB）       |
| **dma-buf (DSP, userspace_rss)** | 5888 MB   | 5501 MB     | 基本持平（ai 高 387 MB）   |
| **合计 ≈ VmRSS + dma-buf** | **10501 MB ≈ 10.3 GB** | **7531 MB ≈ 7.4 GB** | **ai 高 ~2.9 GB（+39%，以 genai 为基线）** |

> [!NOTE]
> **差异已可归因到 CPU 堆（RssAnon），不再是「待补」（据同一批 dmabuf_dump 稳态采样）**
>
> 上表 RssAnon / RssFile 分解与合计值来自**同一批 `dmabuf_dump` 稳态对比**（aiservice 侧 `VoyahAIService` 服务进程、genai 侧 `android_test` 进程；**2026-08-21** 采样，已列入本篇数据来源；与 0902 的 xlsx 为不同批次）。关键事实：
>
> - **两侧 RssFile 几乎相同（1460 vs 1463 MB）、dma-buf 几乎相同（5888 vs 5501 MB）** → 差异**几乎全在 CPU 堆 RssAnon**（aiservice ~3043MB vs genai ~300~540MB，aiservice 在堆里多留一份 ~3GB，观测到两个 ~1.5GB 的 scudo 大块）。
> - **归因结论升级**：genai 更省的本质是**「不把模型在 CPU 堆里再留一份」，省的是 CPU 内存、不是 DSP 内存**。原「差异归因待补」列的三个候选中，**「多 LoRA 预加载（mmap 权重）」已被 RssFile 相同排除**；差异指向 **CPU 堆侧的一份拷贝**（疑为服务端把模型/上下文在堆里再复制一份，**具体根因仍待确认**）。
> - **VmRSS 与 dma-buf 可直接相加的依据**：两者重叠经 `smaps` 验证仅 **~88kB**，故 `合计 ≈ VmRSS + dma-buf` 不存在重复计数。
>
> **采样时机陷阱（重要，否则结论会错）**：genai 的 dma-buf 随推理推进（KV-cache 填充）**持续增长、~12s 才到稳态**，必须在**稳态（≥12s）采样**；早采样（如 ~6s）会**低估 ~1GB**。本项目曾据早采样得出「genai dma-buf 4.4~4.5GB / 合计 6.5GB / 低 38%」的**错误结论，已作废**——稳态下两侧 dma-buf 其实基本相同。另：**不要把 `dmabuf_dump` 的 `dmabuf total`（整机导出量，含 GPU `qcom_hgsl`/显示）当成某进程的内存**，单进程要用 `userspace_rss`（本表已用对口径）。

> [!NOTE]
> **口径澄清（严谨性修正）**
>
> - 原篇阈值行「VmRSS + dma-buf < 10.3GB」与实测行「PSS ~1.85~2.14GB」**口径不同**：前者是 aiservice 形态的 VmRSS+dma-buf 合计（10.3GB 即 aiservice 实测合计值，被用作预算上限），后者是 genai 测试进程的 CPU 侧 PSS。**PSS ≠ VmRSS + dma-buf**，二者不可直接对比，上表已分行呈现。
> - **百分比与换算口径更正**：aiservice 合计 4613+5888=**10501MB**、genai 合计 2030+5501=**7531MB**，差 **2970MB**。以 genai 为基线，aiservice 高 **~2.9GB（+39%）**（2970/7531）；原篇「~27%」实为差值占 aiservice 自身合计的比例（2970/10501≈28%），**不是「高 X%」的口径**，现已统一为以 genai 为基线。MB→GB 换算统一按 **/1024**（原表混用：10.3 按 /1024、7.5 按 /1000，现统一为 ~10.3 / ~7.4）。
> - **①② 不可互比（PSS≤VmRSS 自洽性检查）**：同一进程同一快照恒有 **PSS ≤ VmRSS**。① 的 Total PSS 上界 2.14GB **>** ② 的 genai VmRSS 2030MB≈1.98GB，故 ①② **必然不是同一进程 / 同一采样时刻**（① 是 09-02 6h 连跑期间 genai 测试进程的 PSS 区间，② 是服务形态对比中的稳态值；两者的进程名与采样时刻原文均未注明，**待澄清**）。因此 ①② 不可互比，PSS≤VmRSS 约束仅对同一快照成立。
> - **进程范围待澄清**：aiservice 的 VmRSS 4613MB 测的是**哪个进程**（VoyahAIService 服务进程 / 客户端 / 二者合计）在本篇原材料中未注明（[GenAI vs AIService 篇 §1](genai-vs-aiservice.html) 的口径说明称 aiservice 侧为持模型的 `VoyahAIService` 服务进程、genai 侧为 `android_test` 进程，可作参照），需补充测量范围说明，否则 aiservice vs genai 的 ~2.5GB VmRSS 差异无法解读。
> - **差异归因（已部分坐实，见上方 RssAnon 分解 NOTE）**：aiservice 比 genai 高约 2.9GB，已定位到**几乎全在 CPU 堆 RssAnon**（aiservice 多留一份 ~3GB），RssFile 与 dma-buf 两侧基本相同；**剩余待确认**的是「aiservice 为何在 CPU 堆多留这一份」（疑为服务端把模型/上下文在堆里再复制一份）及有无压缩空间。

### 4.4 稳定性测试

> 数据来源：`performance_test_result.xlsx` 的 `稳定性报告`（2026-09-02 约 6h 连跑）。

- **稳定性结论**：ANR = 0、Java Crash = 0、OOM = 0、Native Crash = 0，6h 连跑通过。
- **高负载下**（stress 2 核、16G）：CPU 占用率持续升高，呈阶段性稳定。
  - *初步猜测（未证实）*：可能由内存高负载导致 CPU 频繁等待（I/O Wait 或内存换页）拉高 CPU 占用率。
- **常规负载**（不设置 stress）：各项指标正常。

> [!WARNING]
> **稳定性结论的覆盖边界与泄漏判据（本轮深挖新增）**
>
> - **只覆盖 genai 形态、不能外推到当前主用的 aiservice 形态**：本 6h 连跑（0902 台架）是 **genai 形态**；而项目最终以 **aiservice 为主用后端**（见 [GenAI vs AIService 篇](genai-vs-aiservice.html)），该形态的稳定性 / soak 数据本篇**未覆盖**，且已知有**客户端槽位泄漏**（见 [AIService 篇](aiservice-integration.html) 的槽位/多客户端问题）。故「6h 连跑通过」**不能外推到当前主用形态**，aiservice 形态需单独补 soak。
> - **「6h 无单调增长」不足以排除慢泄漏**：§4.3① 的 PSS 1.85~2.14GB「6h 无单调增长」是**目视/区间判断**。慢泄漏（如每次数百 KB）在 6h 内可能淹没在 0.29GB 的正常波动里。判据应改为 **24~72h soak + 对 PSS/VmRSS 做线性回归、看斜率（MB/h）及其置信区间是否显著 >0**，而非看首末值或区间是否「单调」。
> - **三个「率」不可混读**：本节稳定性判据（ANR/Crash/OOM = 0）是**故障率**、§2.2 的「识别成功率 100%」是**推理未失败率**、§1.4 的「通过率 86~98%」是**效果准确率**——三者口径完全不同，不可互相替代或混读。
> - **未覆盖的量产最坏情况**：6h 台架连跑未覆盖长时间驻留、前后台切换、多客户端并发、OTA 期间、低温/高温环境等量产工况；稳定性「通过」应限定为「**台架 6h 连跑工况下**通过」。

### 4.5 消融实验设计（阶梯形设置 stress）

> [!WARNING]
> **先纠正本矩阵要回答的问题（方法学误置，本轮深挖新增）**
>
> 原表述「定位 CPU 占用升高的根因（计算瓶颈 vs 内存带宽瓶颈）」是**方法学误置**：
>
> - **注入 stress 改变的是「宿主侧争抢」，不是「推理本身的瓶颈性质」**。用 CPU/内存 stress 去判定「VLM 推理是 compute-bound 还是 memory-bound」不成立——那是 NPU 内核的性质，需 **NPU 侧 roofline/计数器**（CDSP 利用率、DDR 带宽、prefill vs decode 的算术强度，方法见 [LLM 推理原理 · Roofline](../../general/infer-principles.html)）才能判定。
> - **该矩阵真正能回答的是「共存干扰（co-tenancy）下 VLM 推理的退化曲线」**：当 CPU/内存带宽被其它负载（导航/语音/仪表等车机进程）占用时，推理的 TTFT/TPS/Total 如何退化——这是量产车机上真实会发生的，是有价值的问题。
> - **判据要改**：观测量应从「CPU 占用率」改为**推理侧指标**（各阶段 TTFT/TPS/Total 的退化%、成功率）；CPU 占用率只是自变量。且需先明确「CPU 飙升」指**系统总占用**（含车机其他进程，§4.2 为 ~58~61%）还是**推理进程**（仅 ~1~2%）——若指系统总占用，则与 VLM 推理链路**无因果关系**，消融结论无法归因到推理。
> - **缺 NPU 争抢维度**：矩阵只压 CPU/内存，没有「**并发 N 路推理**」组——而 aiservice 形态的真实争抢是**多客户端共享 NPU**（见 [AIService 篇](aiservice-integration.html) 的多客户端/槽位问题）。建议补组 7。
> - **组 5「3/4 核」表述含糊**（3 还是 4 核？）需明确。

为量化**共存干扰下推理的退化**（原目标「定位 CPU 飙升根因」的方法学修正见上方 WARNING），设计了以下阶梯式压力测试矩阵（压力注入使用 `stress` 工具）：

| 实验组别 | CPU Stress | Memory Stress | 状态                      |
| :------- | :--------- | :------------ | :------------------------ |
| 1        | 2 核       | 无            | 待测                      |
| 2        | 2 核       | 4 G           | 待测                      |
| 3        | 2 核       | 16 G          | **已做**            |
| 4        | 0 核       | 16 G          | 待测                      |
| 5        | 3 核（原写「3/4 核」，需明确） | 16 G | 待测                      |
| 6        | No stress  | No stress     | **已做**（基线对照） |
| 7        | No stress  | No stress，**并发 N 路推理**（NPU 争抢） | 待测（建议新增） |

> 目前仅完成「2 核 + 16G」与基线两组，其余组**待测**。**判据**：以推理侧指标（各阶段 TTFT/TPS/Total 退化%、成功率）为观测量，对比组 1（只压 CPU）与组 4（只压内存）即可分离「CPU 争抢」与「内存带宽争抢」对推理的影响——这两组正是分离两种争抢的关键，设计本身是对的，但原「Memory Bound vs Compute Bound」的结论框架需按上方 WARNING 改为「共存干扰退化」框架。要判定推理本身 compute/memory bound，另做 NPU 侧 roofline/计数器 profiling。
