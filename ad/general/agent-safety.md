## 1. 驾驶 Agent 架构

### 1.1 VLM 驾驶范式

以 DriveGPT4、LMDrive、DriveVLM 为代表的**视觉语言模型 (VLM) 驾驶范式**（均为 2023–2024 的奠基工作，如今已是基础设施而非前沿）将自动驾驶重构为一个"看图说话 + 推理决策"的过程：VLM 接收多路摄像头图像，生成场景描述和驾驶推理链 (Chain-of-Thought)，最终输出驾驶决策或控制信号。

```mermaid
flowchart LR
    A["多路摄像头图像<br/>(前/后/左/右)"] --> B["视觉编码器<br/>(ViT / CLIP)"]
    B --> C["投影层<br/>视觉 Token 对齐"]
    C --> D["LLM 推理<br/>(场景理解 + CoT)"]
    D --> E["结构化输出<br/>驾驶决策"]
    E --> F["控制信号<br/>转向/油门/制动"]

    G["导航指令<br/>历史轨迹"] --> D
    H["交通规则<br/>高精地图"] --> D

    style B fill:#4361ee,color:#fff
    style D fill:#2ecc71,color:#fff
    style E fill:#f39c12,color:#fff
```

一个典型的 VLM 驾驶推理过程：

```text
[Input] 前方摄像头图像 + "请分析当前驾驶场景并给出决策"

[VLM Output]
场景描述: 前方 30m 处有一辆白色轿车正在减速，右侧车道有一辆卡车匀速行驶。
当前车道前方约 100m 处有红灯。路面干燥，天气晴朗。
推理: 前车减速可能是因为看到了远处的红灯。右侧车道被卡车占据，不宜变道。
应当跟随前车减速，保持安全车距。
决策: { "action": "follow", "target_speed": 25, "steering": 0, "reason": "前车减速，红灯在前" }
```

VLM 驾驶范式在工程上有两种落地形态（实际方案常混合使用）：

- **VLM 作为"慢思考系统"**：VLM 负责场景理解与决策建议（秒级），实时控制仍由传统快系统承担——DriveVLM (2024) 的 Dual 形态（VLM 慢系统 + 快驾驶网络）是代表。这种形态与 §4.4 的双系统冗余架构天然衔接，是量产上更稳妥的路线。
- **VLM/多模态大模型直接输出轨迹或控制量**：端到端形态，早期代表如 Waymo EMMA（基于 Gemini，研究性质、未量产）与 Wayve LINGO 系列（均 2024）；2025 年起这条线演化为 **VLA (Vision-Language-Action)** 范式并走向量产——多家车企陆续发布自研 VLA 驾驶大模型（如理想的 MindVLA、小鹏的 VLA，均 2025），华为 ADS 4（2025）以云端**世界引擎**+ 车端**世界行为模型**组成 WEWA 架构，NVIDIA 也推出 Cosmos Reason（2025 起）等开源物理 AI 推理模型。各家的公开形态与路线归属见 [BEV 感知与端到端 §6.4](perception.html)。能力上限更高，但安全论证难度也最大（见 §5.5）——**截至 2026 年，VLA 的量产落地速度明显快于其安全验证方法的标准化速度**，这个缺口本身就是当前功能安全领域最活跃的问题。

### 1.2 VLM 驾驶 vs 传统 Pipeline

| 维度 | VLM 驾驶 Agent | 传统感知-预测-规划 Pipeline |
| :--- | :--- | :--- |
| **可解释性** | 表面高 — 生成自然语言推理过程（但忠实性存疑，见下方 CAUTION） | 低 — 各模块输出数值，人难以理解决策逻辑 |
| **泛化能力** | 强 — 预训练知识覆盖 open-world 场景 | 弱 — 仅能处理训练集中见过的场景 |
| **推理延迟** | 高 — 自回归生成 token 逐个输出 | 低 — 前向传播一次性输出 |
| **安全认证** | 极难 — LLM 输出不确定性高，需靠运行时监控兜底（§4.5）与统计证据（§5.5） | 相对可控 — 模块可独立验证（但其中的 DNN 模块同样面临 SOTIF 问题） |
| **长尾场景** | 潜力大 — 常识推理处理未见场景 | 差 — 完全依赖训练数据覆盖 |
| **开发效率** | 高 — prompt engineering 快速迭代 | 低 — 需要大量标注和训练 |
| **硬件需求** | 高 — 7B+ 模型需要强大的 NPU | 中 — 轻量模型即可 |

> [!NOTE]
> **驾驶 Agent 面临"安全长尾"问题**
>
> VLM 驾驶 Agent 的最大挑战不是常规场景的表现 (这方面 LLM 的常识推理能力非常强)，而是**极罕见的安全关键场景**的可靠性。LLM 本质上是一个概率模型，无法提供 100% 的输出保证。一个 0.01% 的错误率在 10 亿次推理中意味着 10 万次错误——对于驾驶场景这是不可接受的。当前的务实方案是将 VLM 作为**辅助决策系统** (Advisory)，而非主控系统。

> [!CAUTION]
> **自然语言推理 ≠ 可信的可解释性**
>
> VLM 输出的 CoT 推理链更像一种"事后叙述"，不保证忠实反映模型真实的决策路径：同一个决策可以配上不同的理由，理由还会被 prompt 措辞引导。因此安全验证**不能把"模型给出了看起来合理的解释"当作决策正确的证据**——最终仍要靠闭环行为测试与统计证据（见 §5）。这是 VLM 驾驶安全论证的核心难题之一。

## 2. 端侧驾驶 Agent 部署

### 2.1 端侧 VLM 推理

将 VLM 部署到车端面临严峻的算力与内存带宽限制。与其记住"某模型在某芯片上多少 tok/s"，不如掌握推导方法——**自回归 decode 的瓶颈通常是内存带宽，而不是算力**。

**Decode 吞吐的带宽模型 (roofline 式推导)**：自回归 decode 每生成 1 个 token，都要把模型权重（外加不断增长的 KV Cache）从内存读一遍。batch=1 时 decode 通常 memory-bound：

```text
单流 decode 吞吐上限 ≈ 内存带宽 (GB/s) ÷ 每 token 需读取的字节数 (GB/token)
每 token 读取字节 ≈ 模型权重字节 + 该步 KV Cache 字节
模型权重字节 ≈ 参数量 × 每参数字节 (FP16=2, INT8=1, INT4=0.5)
```

示例参数（仅演示方法、非实测）：设平台内存带宽 ~200 GB/s，跑一个 7B INT4 模型（权重 ≈ 7×10⁹ × 0.5 B ≈ 3.5 GB），忽略 KV Cache 与调度损失，则单流 decode 上限 ≈ 200 ÷ 3.5 ≈ 57 tok/s。实际再扣除 KV Cache 读取、kernel 启动/调度、prefill 阶段的算力瓶颈，有效吞吐会明显低于该上限。请代入你自己的平台带宽与模型配置计算。

> [!NOTE]
> **Prefill 算力受限、Decode 带宽受限**
>
> - **Prefill**（一次性处理 prompt + 视觉 token）：compute-bound，延迟 ≈ 输入 token 总数 × 每 token FLOPs ÷ 有效算力。
> - **Decode**（逐 token 自回归生成）：memory-bound，每 token 延迟 ≈ 每 token 读取字节 ÷ 内存带宽。
>
> 两段瓶颈不同，延迟预算要分开估，不能混为一谈。

**模型尺寸缩减策略**（本质都是减小"每 token 读取字节"或"token 总数"）：

- **知识蒸馏**：用 70B 模型蒸馏出 3B/1.5B 的驾驶专用模型，保留驾驶场景的推理能力——参数量小，每步读取的权重字节就少
- **INT4 量化**：将 7B 模型从 FP16 (~14 GB) 压缩到 INT4 (~3.5 GB)，每步读取的权重字节降到 1/4，decode 吞吐通常显著提升
- **视觉 Token 压缩**：6 路摄像头的视觉 Token 数量巨大 (如每路 256 tokens = 1536 total)，通过 Perceiver Resampler 压缩到 64 tokens——直接缩短 prefill 长度
- **Speculative Decoding**：用小模型 (1B) 草拟多个 token，大模型 (7B) 并行验证，提升有效吞吐 (代价是额外的验证算力)

### 2.2 场景描述生成

VLM 驾驶 Agent 的输出格式直接影响下游模块的对接效率。两种主要方案：

**结构化输出 (JSON)**：VLM 输出固定格式的 JSON，包含场景元素列表和驾驶决策。优点是下游解析方便、延迟确定；缺点是限制了模型的推理深度和灵活性。

**自然语言输出**：VLM 自由生成场景描述和推理链。优点是推理更深入、更灵活；缺点是需要额外的 NLP 解析步骤，且输出长度不确定。

### 2.3 延迟预算

一次 VLM 驾驶推理可拆成若干**串联阶段**，总延迟是各阶段之和。下表给出每个阶段"由什么决定、怎么估"，而不是填死的数字：

**驾驶 Agent 单次推理延迟分解（方法）**

| 阶段 | 做什么 | 延迟主因 | 估算方法 |
| :--- | :--- | :--- | :--- |
| **视觉编码** | ViT/CLIP 把多路图像编码为视觉特征 | 图像分辨率 × 路数、ViT 规模 | compute-bound：≈ 视觉 token 数 × 每 token FLOPs ÷ 有效算力 |
| **视觉 token 压缩** | Perceiver Resampler 压缩视觉 token | 压缩前/后 token 数 | compute-bound，通常远小于视觉编码 |
| **Prefill** | 一次性处理 prompt + 视觉 token，建立 KV Cache | 输入 token 总数 | compute-bound：≈ 输入 token 数 × 每 token FLOPs ÷ 有效算力 |
| **Decode** | 自回归逐 token 生成输出 | 输出 token 数、内存带宽 | memory-bound：≈ 输出 token 数 × (每 token 读取字节 ÷ 内存带宽) |
| **结构化解析** | 把输出解析为 JSON/决策 | 输出长度、解析方式 | CPU 侧，通常可忽略 (ms 级) |

总延迟 ≈ 视觉编码 + token 压缩 + prefill + decode + 解析。其中 **decode 往往是最大头**（随输出 token 数线性增长），所以压延迟要先压输出长度、再提 decode 吞吐。

VLM 驾驶 Agent 的延迟预算取决于其在系统中的角色。**所需 decode 吞吐 = 输出 token 数 ÷ 延迟预算**，再拿它和 §2.1 带宽模型算出的平台可达吞吐对比，即可判断可行性：

| 角色 | 延迟预算 (示例) | 典型输出长度 | 所需 decode 吞吐 (= token ÷ 预算) | 与端侧带宽上限对比 |
| :--- | :--- | :--- | :--- | :--- |
| **L2+ 辅助 (Advisory)** | <500ms | ~100 tokens | ~200 tok/s | 接近/超过 Orin 级平台 3B INT4 的 decode 上限；需把预算放宽到秒级或缩短输出才稳妥 |
| **L3 决策参与** | <100ms | ~50 tokens (JSON) | ~500 tok/s | 远超当前端侧带宽上限，不可行 |
| **L4 主控决策** | <50ms | ~20 tokens | ~400 tok/s | 远超当前端侧带宽上限，不可行 |

表中"所需 decode 吞吐"把**整个延迟预算都算给了 decode**，这是偏乐观的口径——视觉编码与 prefill 同样要吃掉预算（见上表的阶段分解），留给 decode 的时间更少，因此实际所需吞吐比表中更高。也就是说，表里"不可行"的结论是**保守成立**的，不会因为把 prefill 算进去而翻盘。

另外，表中的 L2+/L3/L4 沿用行业习惯说法，其正式定义来自 **SAE J3016**（L0–L5 驾驶自动化分级）与中国对应的 **GB/T 40429-2021《汽车驾驶自动化分级》**。分级的实质差别是**"谁是驾驶主体、谁负责监控"**：L2 由驾驶员持续监控（系统只是辅助），L3 起由系统在其 ODD 内承担动态驾驶任务、驾驶员作为后备，L4 起系统在 ODD 内不需要人类后备。这个差别直接决定了 §4.4 的 fail-safe / fail-operational 选型，也决定了适用哪套准入法规（§5.6）。

> [!NOTE]
> **端侧硬件可以支持 VLM 辅助决策，但无法支持实时主控**
>
> 判断依据是上面的推导，而不是记结论：**可行输出长度 ≈ decode 吞吐 × 延迟预算**。若你的平台代入带宽与模型尺寸后 decode 吞吐在几十 tok/s 量级，那么 500ms 预算内只能生成十几到几十个 token——足够输出一句简短建议 (如"前方施工，建议变道")，但不足以支撑需要 <100ms 的实时决策长推理链。
>
> 实时主控 (L3+) 与端侧自回归 VLM 之间还差一个数量级。务实路线是：把辅助角色的延迟预算放宽到秒级、缩短输出，等待更高内存带宽的新平台（如 NVIDIA Drive Thor，2025 年起已量产上车），或改用非自回归/结构化一次性输出的方案。

## 3. V2X 与云端协同

### 3.1 车-边-云架构

自动驾驶不是单车智能就能完全解决的——**V2X (Vehicle-to-Everything)** 和云端协同为车端智能提供了超视距感知、全局规划和持续进化的能力。

```mermaid
flowchart TB
    subgraph Vehicle["车端 (Vehicle)"]
        VP["感知推理<br/>BEV + 3D Det"] --> VPL["本地规划<br/>实时路径"]
        VPL --> VC["控制执行<br/>转向/制动"]
    end

    subgraph Edge["边缘服务器 (RSU)"]
        EM["路侧感知融合<br/>超视距目标"] --> EI["交通信息聚合<br/>信号灯/事故"]
        EI --> EU["地图局部更新<br/>施工/管制"]
    end

    subgraph Cloud["云端 (Cloud)"]
        CT["模型训练<br/>数据飞轮"] --> CM["车队管理<br/>OTA 更新"]
        CM --> CA["全局规划<br/>交通调度"]
    end

    Vehicle <-->|"C-V2X PC5: ~20ms (示例)"| Edge
    Edge <-->|"5G 回传: ~50ms (示例)"| Cloud
    Vehicle <-->|"4G/5G Uu: ~500ms (示例)"| Cloud

    style VP fill:#4361ee,color:#fff
    style EM fill:#2ecc71,color:#fff
    style CT fill:#9b59b6,color:#fff
```

C-V2X 定义了两种互补的通信模式：**PC5 直连通信**（车-车/车-路/车-人直连，不依赖蜂窝网络覆盖，低时延，承载安全预警类消息）与 **Uu 蜂窝模式**（经基站接入网络/云端，覆盖广、带宽大，承载地图更新与云服务）。这个区分直接影响断网降级设计：蜂窝覆盖丢失时 PC5 直连仍可在邻近车辆与 RSU 之间工作——§3.3 的"断网"要区分"与云端断开"和"蜂窝覆盖丢失"，PC5 安全预警不一定同时失效。

### 3.2 通信延迟与功能分配

不同功能对通信延迟有不同的容忍度，这决定了该功能应部署在车端、边缘还是云端：

| 功能 | 延迟容忍 | 部署位置 | 通信方式 | 断网后果 |
| :--- | :--- | :--- | :--- | :--- |
| **紧急避障** | <10ms | 车端 (Safety Island) | 无需通信 | 无影响 |
| **实时路径规划** | <50ms | 车端 (CPU) | 无需通信 | 无影响 |
| **V2X 安全预警** | <20ms | 车端处理（消息来自邻车/RSU） | C-V2X PC5 直连 | 丧失超视距预警 |
| **信号灯状态** | <100ms | 边缘 (RSU) | C-V2X / 5G | 回退到视觉识别 |
| **高精地图更新** | <500ms | 边缘/云端 | 5G | 使用缓存地图 |
| **模型 OTA 更新** | 分钟级 | 云端 | 4G/5G/WiFi | 延迟更新 |
| **车队数据回传** | 小时级 | 云端 | WiFi (充电时) | 缓存后补传 |

表中延迟容忍与通信方式为**示例口径**（用于说明功能分配方法），实际指标应由安全目标的 FTTI（可容忍故障时间间隔，见 §4.2）与端到端时序预算推导。

V2X 的"说什么"由标准化消息集定义，做功能分配时要按消息类型而非笼统的"V2X"来算延迟预算：**SAE J2735** 定义了 **BSM**（基本安全消息，周期广播车辆自身状态）、**SPaT**（信号灯相位与配时）、**MAP**（路口几何）、**RSI/RSM**（路侧信息/路侧感知）等；**ETSI ITS** 侧对应 **CAM**（协同感知消息，周期广播）、**DENM**（事件触发的分布式环境通知）、**CPM**（融合后目标的协同感知消息）。安全预警类走周期/事件广播、要求低时延高可靠；地图与信息服务类可走蜂窝、容忍更大时延——这正是上表"部署位置"分列的依据。中国的应用层消息标准由 T/CSAE 系列与相关国标规定（具体编号与版本**需核实**）。

> [!NOTE]
> **OTA 与数据回传不只是工程问题，还是合规问题**
>
> - **网络安全与 OTA**：UNECE **R155**（网络安全管理体系，CSMS）与 **R156**（软件升级管理体系，SUMS）已在欧盟等市场强制实施——表中的"模型 OTA 更新"必须走 R156 要求的版本管理、验证与回滚流程。中国对应的强制性国家标准 **GB 44495-2024**（汽车整车信息安全技术要求）与 **GB 44496-2024**（汽车软件升级通用技术要求）已于 **2026-01-01 起正式实施**；同批发布的 **GB 44497-2024**（智能网联汽车 自动驾驶数据记录系统）要求记录自动驾驶系统状态与接管信息，既是事故归因的依据，也是 §5 数据飞轮与场景挖掘的合规数据来源（编号与实施日期**需核实**）。
> - **AI 监管**：欧盟《人工智能法案》(**Regulation (EU) 2024/1689**) 于 **2024-08-01 生效**、分阶段适用——禁止性行为自 **2025-02**、通用目的模型 (GPAI) 义务自 **2025-08**、Annex III 高风险系统义务自 **2026-08**、Annex I 受监管产品（含车辆）内嵌的高风险 AI 自 **2027-08**。车载 AI 主要走 Annex I 这条型式认证路径，由既有车辆法规体系承接符合性评估。完整法规框架表见 [座舱数据合规与评估 §1.2](../../cockpit/general/data-pipeline.html)。
> - **数据回传**：车队数据回传与数据飞轮涉及地图测绘、个人信息与重要数据，在中国需符合《汽车数据安全管理若干规定（试行）》（2021 年施行）等要求，遵循"车内处理、默认不收集、脱敏处理"等原则。

### 3.3 断网降级策略

车端系统必须在**完全断网**情况下仍能安全运行。降级策略：

- **感知**：回退到纯车载传感器模式，丧失超视距感知但保留本地感知能力
- **地图**：使用本地缓存的先验地图（示例参数：当前路线 + 周边数十公里），但缓存可能不是最新的
- **规划**：切换到保守驾驶模式——降低速度、增加安全距离、避免复杂路口
- **VLM Agent**：完全在本地运行 (使用端侧量化模型)，不依赖云端大模型

> [!NOTE]
> **"断网降级"的前提是先降低对先验信息的依赖**
>
> 2025 起量产主流已从"重高精地图"转向**轻地图/无图**路线——用在线感知实时构建局部矢量地图（车道线、路沿、可行驶区域），把先验地图降级为"有则更好"的增强信息（原理见 [BEV 感知与端到端](perception.html)）。这在安全上是一种**结构性降级设计**：系统的正确性不再绑定在一个可能过期、可能无覆盖、可能断网取不到的外部数据源上。
>
> 反过来说，如果方案仍强依赖高精地图，那么"地图不可用/地图过期"就必须被建模为一个**显式的 ODD 边界条件**并配套退出策略（§5.1），而不是靠"缓存几十公里"糊过去——缓存只能解决"取不到"，解决不了"取到的是错的"（施工改道、车道线重画）。

> [!NOTE]
> **V2X 是增强而非依赖**
>
> V2X 提供的能力 (超视距感知、交通信号、地图更新) 是对车端智能的**增强**，而非替代。任何依赖 V2X 通信的功能都必须有本地 fallback 方案。这是自动驾驶安全设计的基本原则：**单车智能保底，V2X 锦上添花**。

## 4. 功能安全 (ASIL)

### 4.1 ASIL 等级体系

ISO 26262 定义的 **ASIL (Automotive Safety Integrity Level)** 等级从 A 到 D，D 为最严格。ASIL 等级由三个因素的组合决定：**严重度 (Severity)**、**暴露度 (Exposure)**、**可控性 (Controllability)**。

| ASIL 等级 | 典型场景 | PMHF 失效率要求 | 开发要求 | 代表功能 |
| :--- | :--- | :--- | :--- | :--- |
| **QM** | 非安全功能 | 无要求 | 标准质量管理 | HMI 显示、娱乐系统 |
| **ASIL-A** | 低伤害风险 | <1000 FIT (10⁻⁶/h)（仅 2011 版规定，见下方 NOTE） | 基本安全流程 | 后车灯控制、雨刷 |
| **ASIL-B** | 中等伤害风险 | <100 FIT (10⁻⁷/h) | 较严格验证 | 座椅加热、部分 BMS 监控、DMS 报警 |
| **ASIL-C** | 严重伤害风险 | <100 FIT (10⁻⁷/h) | 严格验证+测试 | 电池热失控预警/热管理互锁（视危害而定） |
| **ASIL-D** | 危及生命 | <10 FIT (10⁻⁸/h) | 最严格全流程 | 线控制动/线控转向、EPS 助力转向、ESC、安全气囊起爆、AEB 相关安全目标、自动驾驶安全监控 |

其中 FIT = Failure In Time，1 FIT = 10⁻⁹ 故障/小时。ASIL-D 的 PMHF <10 FIT (即 10⁻⁸/h) 意味着系统平均**连续运行约 1.14 万年** (10⁸ 小时) 才发生 1 次危险硬件故障。

表中代表功能只是行业常见的**示例口径**，不是认证结论：同一功能在不同车型/不同 ODD 下定级可能不同，一切以具体 item 的 HARA 为准（见 §4.2）。三个常见误定级要注意：

- **ESC 稳定控制、安全气囊起爆、EPS 助力转向通常定为 ASIL D**——稳定性失控、气囊异常起爆、转向助力丢失或异常助力都属危及生命的危害，不宜随手放进 ASIL B/C；
- **AEB 的 ASIL 取决于具体危害，不能笼统给一个等级**："该制动时未制动"本质是性能不足，更多落在 SOTIF 管辖（§5.1）；而"高速行驶中误触发制动"是典型的功能安全危害，通常定到 ASIL C/D。把 AEB 直接说成"ASIL-X"而不指明是哪条危害，是不严谨的；
- **ASIL A 的 PMHF 目标值只在 ISO 26262:2011 版中存在**，2018 版已取消（见下方 NOTE）。

> [!NOTE]
> **ASIL-B 与 ASIL-C 的 PMHF 目标相同，区别在 SPFM/LFM 与开发严格度**
>
> ISO 26262 给 B 和 C 的 PMHF 目标都是 <10⁻⁷/h (<100 FIT)，它们的差异体现在单点故障指标 SPFM、潜伏故障指标 LFM 以及开发/验证流程的严格程度上：
>
> | 硬件概率指标 | ASIL-B | ASIL-C | ASIL-D |
> | :--- | :--- | :--- | :--- |
> | **SPFM** (单点故障指标) | ≥90% | ≥97% | ≥99% |
> | **LFM** (潜伏故障指标) | ≥60% | ≥80% | ≥90% |
> | **PMHF** (随机硬件失效概率) | <10⁻⁷/h | <10⁻⁷/h | <10⁻⁸/h |
>
> 把 ASIL-C 误写成 <10 FIT、ASIL-D 误写成 <1 FIT，是常见的"整体左移一档"错误——记住锚点：**D 是 10⁻⁸/h = 10 FIT，C/B 是 10⁻⁷/h = 100 FIT，A 是 10⁻⁶/h = 1000 FIT**。
>
> 另一个易被忽略的版本差异：**ISO 26262-5:2018 版已不再为 ASIL A 规定 PMHF/SPFM/LFM 目标值**——"A 是 10⁻⁶/h = 1000 FIT"出自 **2011 版**，工程文档中仍常作参考引用，但引用时要注明版本。

### 4.2 从 HARA 到安全需求：推导链与 ASIL 分解

ISO 26262 的安全需求不是拍脑袋定的，而是沿 V 模型逐层推导，ASIL 只是这条链上每一层需求的"风险等级标签"：

```mermaid
flowchart LR
    A["Item Definition<br/>系统边界与功能"] --> B["HARA<br/>危害分析与风险评估"]
    B --> C["Safety Goal<br/>安全目标 + ASIL"]
    C --> D["FSC<br/>功能安全概念"]
    D --> E["TSC/TSR<br/>技术安全需求<br/>分配到硬件/软件"]
    E --> F["实现 + V&V"]
    F --> G["Safety Case<br/>安全证据汇总"]

    style B fill:#4361ee,color:#fff
    style C fill:#e74c3c,color:#fff
    style G fill:#2ecc71,color:#fff
```

- **HARA**：对 item 的每个"功能危害"（如非预期加速、错误转向干预、制动迟滞）按三个维度评估——**严重度 S (S0–S3)**、**暴露度 E (E0–E4)**、**可控性 C (C0–C3)**——经 ISO 26262-3 的风险矩阵映射为 QM / ASIL A–D。§4.1 的三因素即来源于此。
- **Safety Goal（安全目标）**：由危害推导出的顶层安全需求（如"系统不得产生持续的非预期加速"），带 ASIL 等级，并定义安全状态与 **FTTI（Fault Tolerant Time Interval，可容忍故障时间间隔）**——从故障发生到必须进入安全状态的最大时间窗。工程上它被进一步拆成 **FTTI ≥ FDTI（故障检测时间）+ FRTI（故障响应时间）**：FDTI 决定监控器的检测周期与算法延迟上限，FRTI 决定执行器从收到指令到进入安全状态的耗时。§4.6 看门狗的超时上限、§2.3 的延迟预算，最终都要落回到这条不等式上。
- **FSC → TSC**：功能安全概念回答"需要哪些安全功能"（如扭矩监控、驾驶员超驰优先）；技术安全需求回答"系统如何实现"——分配到具体硬件/软件组件，带诊断覆盖率、响应时间等量化要求。

**ASIL 分解 (ASIL Decomposition)** 是让高 ASIL 需求工程可落地的关键机制：一条高 ASIL 需求可以拆到两条（或多条）**足够独立**的冗余路径上共同满足。ISO 26262-9 给出的合法分解组合是固定的，不能任意拆：

| 原 ASIL | 合法分解 |
| :--- | :--- |
| **ASIL D** | C(D) + A(D) ／ B(D) + B(D) ／ D(D) + QM(D) |
| **ASIL C** | B(C) + A(C) ／ C(C) + QM(C) |
| **ASIL B** | A(B) + A(B) ／ B(B) + QM(B) |
| **ASIL A** | A(A) + QM(A) |

括号里的 "(D)" 表示这些路径都源自同一个 ASIL D 安全目标。分解有两个硬性前提：其一，**独立性必须论证**——需要做相关失效分析 (DFA) 排除共因失效（共用电源、时钟、软件库、温度环境都可能是共因源）；其二，**分解不降低安全目标**——它只发生在需求分配层面，安全目标本身的 ASIL 不变。

§4.4 的"QM 主系统 + ASIL-D 安全监控"双系统架构，正是 `ASIL D(D) + QM(D)` 这条分解的工程化体现：性能路径可以 QM，安全目标由独立的监控路径兜底。

### 4.4 双系统冗余

**主系统 (Primary)**：高性能 GPU/NPU，运行完整的感知-预测-规划 pipeline，提供最优驾驶体验。安全等级 QM。

**备用系统 (Backup)**：低功耗安全 MCU (如 Cortex-R5F)，运行简化的安全算法 (如基于传统 CV 的障碍物检测 + 紧急制动)。安全等级 ASIL-D。备用系统的算力有限 (示例参数：<1 TOPS)，但响应确定 (示例参数：<5ms) 且通过完整的安全认证。

双系统冗余的核心难点不是"有两套系统"，而是**仲裁：谁有控制权、何时切换、如何避免争抢**。

**仲裁权必须落在独立于主系统的元素上**。如果"谁说了算"这个判断本身跑在主系统里，主系统失效时仲裁器一起失效——那是共因失效，不是冗余。工程上仲裁通常落在三个位置之一（可叠加）：

| 仲裁位置 | 机制 | 优点 | 代价 |
| :--- | :--- | :--- | :--- |
| **独立安全 MCU** | 安全岛对主系统输出做合理性/超时检查，异常时切断主系统到执行器的通路 | 独立性最强，可做到 ASIL D | 要给出替代动作，就得有独立的传感器与状态估计 |
| **执行器侧门控** | 线控制动/转向 ECU 自带 ASIL-D 安全逻辑，拒绝越界或无有效令牌的指令 | 最后一道防线，不依赖上层存活 | 只能"拒绝"，不能"替代决策" |
| **总线/令牌仲裁** | 双通道总线 + 指令带序列号/存活计数/E2E 校验，执行器只认最新有效帧 | 天然防"僵尸指令"与丢帧 | 需要全链路支持 E2E 保护（§4.6） |

**切换逻辑的三条硬约束**：

- **监控器不复刻完整驾驶功能**：它对主系统输出做合理性检查（范围/变化率/一致性）与超时监控，异常时触发接管——它有权**否决**，但不负责**重新决策**（见 §4.5）；
- **接管判据必须确定且带迟滞/去抖**，避免主备在临界条件下来回震荡；并且**降级后不应自动回升到全功能**——恢复必须走显式的条件检查（甚至要求停车后复位），否则震荡只是以更长的周期重现；
- **接管后执行 MRM (最小风险策略)**，把车带入 MRC (最小风险状态)——如本车道内受控减速停车或靠边停车，而不是简单"断电"。

**Fail-operational 要求备用系统"热备"而非"冷备"**：单点故障后仍要能继续运行并完成 MRM，意味着备用系统的定位与障碍物状态估计必须**持续独立维护**（不能等切换时才从零启动），并配套独立的供电与通信通路。这也是 L4 冗余方案普遍带一套独立传感器套件与双电源的根本原因——**冗余的成本大头不在算力，而在"独立性"**。

另一对易混淆的概念：**Fail-safe** 指故障后系统告警并把控制权交还驾驶员（L2 可接受）；**Fail-operational** 指单点故障后系统仍能继续运行并完成 MRM（L3+ 必须——不能假设驾驶员能瞬间接管）。这是 L3+ 系统的冗余设计要求远高于 L2 的根本原因，也是 §2.3 里 L 分级不只是"能力差异"而是"责任差异"的体现。

### 4.5 大模型输出的运行时安全监控

§4.3/§4.4 的安全监控面对传统 pipeline 时，检查的是"数值是否在合理范围"。面对 VLM/VLA 这类生成式模型，监控要解决的问题更根本：**输出空间是开放的、长度是不确定的、同一个输入可能给出不同输出**。因此监控必须分层，且每一层都只回答"能不能放行"，不回答"应该改成什么"。

| 层 | 检查什么 | 典型手段 | 不通过时的动作 |
| :--- | :--- | :--- | :--- |
| **契约层** | 输出是否符合预定义格式与动作空间 | 受限解码 / grammar-constrained decoding、JSON Schema 校验、动作枚举白名单 | 判为无效，丢弃本次输出 |
| **包络层** | 数值是否在物理与法规边界内 | 速度/加速度/曲率上限、ODD 限速、变化率限幅 | 裁剪到边界内，或直接否决 |
| **可行性层** | 轨迹是否可被车辆执行、是否安全 | 运动学/动力学可行性检查、安全距离模型（RSS 类，已由 IEEE 2846 标准化） | 否决并触发保守动作 |
| **一致性层** | 与独立信息源是否冲突 | 与传统感知/雷达通路交叉比对、多帧时序一致性 | 冲突时走保守分支（宁可误减速） |
| **不确定性层** | 模型自身是否"没把握" | 输出置信度/熵、多次采样一致性、输入 OOD 检测 | **弱信号**，只用于触发降级与记录 |
| **时限层** | 是否在预算内产出 | 每帧 deadline，超时即放弃 | 沿用上帧结果或进入保守模式 |

> [!CAUTION]
> **监控器只能"否决"，不能"修正"**
>
> 这是把不确定输出关进确定笼子的核心原则。一旦监控器否决了模型输出，正确动作是**执行预定义的保守策略**（保持车道减速、MRM、请求接管），而不是让监控器自己"猜"一个替代决策——猜出来的决策同样没有经过安全论证，只是把不确定性从模型搬进了监控器。
>
> 同理，**不确定性层的信号不能单独作为放行依据**：置信度高不等于决策正确（模型可以自信地错），置信度低也不等于危险。它的正确用法是**触发降级与留痕**，而不是参与"这次能不能过"的裁决。

**交叉校验的参照通路必须真正独立**。用同一个视觉编码器、同一份训练数据、同一套软件栈产出的"第二路结果"去校验第一路，只能发现随机性错误，发现不了系统性偏差——§4.2 的 DFA（相关失效分析）同样适用于此。有效的交叉校验要么换传感器模态（雷达/激光对视觉），要么换算法族（传统几何方法对学习方法）。

**自回归生成还带来一个传统系统没有的问题：输出长度不确定 → 完成时间不确定**。这意味着 deadline 必须是硬性的，且"超时"本身要被建模为一个**正常且高频发生的工况**（而不是异常）——系统必须在"这一帧没算完"的情况下依然安全。这也是 §2.3 里"实时主控不可行"的另一面：不只是吞吐不够，而是**时延不可预测**本身就与确定性安全监控相冲突。

### 4.6 Watchdog 机制

| 看门狗类型 | 监控对象 | 超时时间 | 触发动作 |
| :--- | :--- | :--- | :--- |
| **软件 WDT** | 应用进程心跳 | 50-200ms | 进程重启 / 降级 |
| **硬件 WDT** | CPU/OS 存活 | 100-500ms | 系统复位 / 安全停车 |
| **Flow Monitor** | 数据流完整性 | 帧级 (33-100ms) | 丢帧告警 / 切换备用源 |
| **Deadline Monitor** | 任务完成时间 | 按任务定义 | 跳过当前帧 / 使用上帧结果 |

表中超时时间为**示例区间**，实际标定的上限是对应安全需求的 FTTI（§4.2），下限是任务周期。这套监控与 AUTOSAR **PHM (Platform Health Management)** 的三种监督模式对应：**Alive Supervision**（存活，即软/硬件 WDT）、**Deadline Supervision**（时限，即 Deadline Monitor）、**Logical Supervision**（逻辑顺序，即 Flow Monitor 这类跨步骤的数据流/程序流检查），三者组合才构成完整的程序流监控。

> [!NOTE]
> **看门狗管"还活着吗"，E2E 保护管"数据对吗"**
>
> 看门狗只能发现"任务没跑 / 跑太慢 / 顺序错了"，发现不了"任务按时跑完但数据是错的"。后者靠 AUTOSAR **E2E 保护库**：在跨核/跨 ECU 的数据上附加 CRC、存活计数器 (Alive Counter) 与超时检查，接收方校验通过后才使用——这也是 §4.4 总线仲裁那一行的技术基础。
>
> 但对 VLM 这类输出本身就不可信的场景，要清楚 E2E 的能力边界：**它只能保证"传输没坏"，保证不了"内容正确"**。内容正确性要靠 §4.5 的分层监控。两者不可互相替代——把 E2E 校验通过当成"模型输出可信"，是集成阶段很容易犯的错误。

> [!CAUTION]
> **ASIL-D 不只是一个数字，而是全流程安全管理**
>
> 达到 ASIL-D 不仅仅是写好代码——它要求**全流程**的安全管理：危害分析与风险评估 (HARA)、安全概念 (Safety Concept)、技术安全要求 (TSR)、软件/硬件安全需求、相关失效与硬件安全分析 (FMEA/FTA/DFA)、安全验证 (V&V)，最终把所有安全证据汇总成 **Safety Case（安全论证）**，并经过独立的确认措施评审与第三方认证。§4.1 的 PMHF <10 FIT (10⁻⁸/h) 只是这条链上的一个硬件指标。这是为什么自动驾驶安全认证的成本远超算法开发本身。

## 5. 仿真验证与测试

### 5.1 SOTIF (ISO 21448)

**SOTIF (Safety Of The Intended Functionality)** 关注的不是传统功能安全中的"硬件/软件故障"，而是**在没有故障的情况下，系统功能本身的局限性导致的安全风险**。这对 AI 驱动的自动驾驶尤为重要——DNN 模型在训练分布外的场景可能产生错误输出，即使硬件和软件都在正常工作。ISO 21448 于 2019 年首次发布，现行版本为 **ISO 21448:2022**。

SOTIF 与 ISO 26262 的分工是功能安全里最容易混淆的一点，两者**互补而不替代**——一个系统必须同时满足二者：

| | ISO 26262 (功能安全) | ISO 21448 (SOTIF) |
| :--- | :--- | :--- |
| **管什么** | **E/E 系统失效**导致的不合理风险 | **无失效时功能不足/性能局限**导致的危害事件 |
| **典型触发** | 硬件随机失效、软件系统性缺陷、供电丢失 | AI 感知局限 (误检/漏检)、传感器物理极限 (眩光/暴雨)、ODD 边界、可预见的误用 |
| **核心方法** | HARA → ASIL → 安全需求 → 硬件概率指标 (SPFM/LFM/PMHF) | 场景空间四象限分析 (见下) → 验证覆盖度 + 残余风险论证 |
| **对 AI 的适用性** | 流程与指标不为数据驱动模型设计——ML 组件的"失效"表现为性能不足，难以套用传统故障模型 | 天然面向 AI/感知的性能局限 |

针对 AI/ML 组件，两者之间还有一层桥接标准：

- **ISO/PAS 8800:2024《道路车辆 — 安全与人工智能》**（2024 年 12 月以 PAS 形式发布，归口 ISO/TC 22/SC 32）：把安全生命周期方法扩展到 AI，覆盖 **ML 安全生命周期**——数据（训练/校准/评测集）安全要求、模型开发、验证确认、SOP 后监控与持续改进，并与 ISO 26262（系统性失效）、ISO 21448（性能局限）衔接。这是目前对端到端/大模型驾驶系统做安全论证时最直接的 AI 安全标准依据；后续修订与配套标准的动态**需核实**。
- **ISO/IEC TR 5469:2024《功能安全与 AI 系统》**（归口 ISO/IEC JTC 1/SC 42，是**通用功能安全侧**而非道路车辆专用）：按 AI 在安全相关功能中承担的角色对 AI 系统分类，给出"哪类 AI 能用在什么安全场景、需要哪些额外措施"的框架，可与 8800 对照使用（分类命名与判据**需核实**）。

两者分工：**8800 回答"道路车辆怎么做 AI 安全生命周期"，5469 回答"AI 系统在功能安全里能扮演什么角色"**——前者是行业落地指南，后者是跨行业的方法论输入。

> [!NOTE]
> **SOTIF 与 AI 的关系：不是"AI 专用标准"，而是"无故障也会出事"的标准**
>
> 常见误解是把 SOTIF 当成"AI 安全标准"。准确说法是：SOTIF 管的是**功能不足 + 触发条件**这一类风险，而 AI 组件恰好是这类风险的最大来源——因为 DNN 的错误不表现为"坏了"，而表现为"在某种输入下不够好"。所以：
>
> - **传统 CV 算法同样受 SOTIF 管辖**（逆光下的相机、雨天的激光雷达都在 Area 2），不是只有 AI 才需要；
> - **SOTIF 不给 ASIL**，它用"残余风险是否可接受"论证，方法是场景空间收敛 + 验证覆盖度，而不是 SPFM/LFM/PMHF 这类概率指标；
> - **对生成式模型，SOTIF 的难点被放大**：传统感知的触发条件还能枚举（光照/天气/遮挡），VLM/VLA 的触发条件包含 **prompt 措辞、上下文顺序、采样随机性**这类"输入语义"维度，场景空间的维度爆炸更严重——这也是 §5.3 强调多来源场景库、§5.5 强调统计证据而非穷举证明的原因。

SOTIF 分析的核心框架将场景空间划分为四个区域：

| 区域 | 已知? | 安全? | 描述 | 应对策略 |
| :--- | :--- | :--- | :--- | :--- |
| **Area 1** | 已知 | 安全 | 系统能正确处理的常规场景 | 标准测试覆盖 |
| **Area 2** | 已知 | 不安全 | 已知的系统局限性 (如大雾时感知失效) | 设计限制 (ODD) + 降级策略 |
| **Area 3** | 未知 | 不安全 | 未知的不安全场景 (最危险) | 持续测试发现 + 数据飞轮 |
| **Area 4** | 未知 | 安全 | 未测试但实际安全的场景 | 无需特别关注 |

SOTIF 的目标是**同时缩小 Area 2 (已知不安全) 和 Area 3 (未知不安全)**：Area 2 靠设计限制 (ODD) 与降级策略压缩，Area 3 靠系统性场景分析、大规模仿真、实车路测和数据飞轮持续发现来压缩。只盯着 Area 3 是不完整的——Area 2 同样是必须收敛的不安全场景。

> [!NOTE]
> **AI 系统会让测试金字塔"变形"**
>
> 传统金字塔的底座是单元测试——它隐含假设"逻辑写在代码里，逐函数验证就能覆盖大部分风险"。但 DNN/VLA 组件的"逻辑"在权重里，单元测试无从下手：你没法给一个卷积核写断言。于是验证重心从**代码覆盖**转向三件事：
>
> - **数据集覆盖**：训练/校准/评测集的构成、标注质量、分布代表性、污染检查——这是 ISO/PAS 8800 数据侧安全要求的落点；
> - **场景覆盖**：用场景库而非测试用例来定义"测了什么"（§5.3）；
> - **性能门槛**：以指标阈值 + 统计置信度替代"通过/失败"的二值断言。
>
> 结果是金字塔底座变薄、中段（SIL 场景化仿真）变厚。这不是偷懒，而是黑盒组件的验证只能靠"输入空间采样 + 输出统计"，不能靠"内部逻辑遍历"。也因此，**"代码覆盖率 100%"在 AI 系统里不再等于安全**——它只说明推理代码的每一行都被执行过，不说明模型的每一种行为都被检验过。

### 5.3 场景化测试

自动驾驶的测试不是简单的"跑多少公里"，而是**场景化测试 (Scenario-based Testing)**——构建覆盖各种交通场景的测试库，系统性验证系统在每种场景下的表现。

**场景库构建**：

- **标准场景库**：基于 Euro NCAP、C-NCAP 等测评规程，以及 ISO 3450x 系列（自动驾驶测试场景标准族）定义的测试场景 (如 AEB 行人横穿、LKA 弯道保持)
- **数据驱动场景**：从实车数据中提取的真实交通场景，参数化后生成大量变体 (改变车速、距离、角度等)
- **对抗场景**：使用对抗生成方法自动搜索系统最容易失效的场景参数组合
- **世界模型与神经重建**：用世界模型与神经场景重建 (NeRF/3DGS) 做场景生成——把真实 corner case 重建成可编辑的仿真资产，或用生成式模型直接合成新的场景变体，缓解"长尾场景测不完"的问题。2025 年起进入规模化应用：NVIDIA Cosmos (2025) 提供开放的世界基础模型平台，Wayve GAIA-2 (2025) 面向驾驶做可控多视角场景生成（世界模型原理见 [BEV 感知与端到端](perception.html)）
- **组合爆炸**：天气 (晴/雨/雪/雾) x 光照 (白天/黄昏/夜晚) x 道路 (直线/弯道/路口) x 目标 (车辆/行人/自行车) = 海量组合

场景要能在不同仿真工具间可执行、可比较，需要统一的描述格式与标准族：

- **ASAM OpenDRIVE**（静态路网）与 **ASAM OpenSCENARIO**（动态场景：交通参与者的行为与交互）是行业事实标准。OpenSCENARIO 有两条线：**1.x 是 XML，描述"具体怎么演"**（带确定参数的动作序列）；**2.0 是领域特定语言 (DSL)，描述"要满足什么约束"**（抽象场景 + 参数空间），更适合做大规模参数化变体生成与组合覆盖。
- **ISO 3450x 系列**给出方法学骨架：34501（术语）、34502（ODD 规范）、34503（ODD 分类学）、34504（测试用例）、34505（场景化安全评估框架）——其中 34502/34503 管"ODD 怎么定义和分类"，34504/34505 管"场景怎么变成可执行的测试与评估"（各分册的确切标题与发布年份**需核实**）。

**覆盖度指标**：

| 覆盖维度 | 指标 | 目标 |
| :--- | :--- | :--- |
| **场景类型覆盖** | 覆盖的标准场景数 / 总标准场景数 | >95% |
| **参数空间覆盖** | 测试过的参数组合 / 总参数空间 | >80% (关键区域 100%) |
| **ODD 边界覆盖** | 测试过的 ODD 边界条件 / 总边界条件 | 100% |
| **代码覆盖** | 被测试执行的代码行数 / 总代码行数 | >90% (安全关键 100%) |

表中目标值为**示例口径**——覆盖度没有放之四海皆准的"及格线"，实际验收标准应按项目定义，并在 Safety Case 中论证其充分性。

> [!CAUTION]
> **覆盖率的分母才是真问题**
>
> "场景类型覆盖 >95%" 这类指标只在**场景库本身完备**时才有意义。如果库不全，覆盖率 100% 也照样漏掉 Area 3（§5.1）——你无法度量你不知道的东西。因此覆盖度需要一个**元指标：场景库来源的多样性**。单一来源的库再大都有系统性盲区：
>
> - 只用**标准/测评规程** → 覆盖"法规关心的"，漏掉真实交通里的怪异交互；
> - 只用**实车数据挖掘** → 覆盖"已经发生过的"，天然漏掉从未发生的严重事件（幸存者偏差）；
> - 只用**对抗搜索** → 覆盖"模型最弱的"，但找到的可能是不具现实性的病态样本；
> - 只用**世界模型生成** → 覆盖"生成器认为可能的"，受生成器自身先验限制。
>
> 务实做法是**多来源并行 + 交叉补盲**，并在 Safety Case 里论证"为什么这组来源足以覆盖目标 ODD"，而不是只报一个覆盖率数字。

### 5.4 HIL/SIL 测试架构

**SIL (Software-in-the-Loop)**：完整的自动驾驶软件栈运行在 PC/服务器上，传感器数据完全由仿真器 (如 CARLA、51Sim 等；曾经常用的 LGSVL/SVL 已停止维护) 生成。优势是可以大规模并行运行 (数百个实例)，一天内跑完数百万个场景。

**HIL (Hardware-in-the-Loop)**：自动驾驶软件栈运行在真实的域控制器硬件上，传感器数据由仿真器通过高速接口注入。验证的是**真实硬件上的性能和时序**——SIL 中可能不出问题的延迟/内存/调度问题，在 HIL 中会暴露。

| 测试级别 | 验证内容 | 典型覆盖场景数 | 执行时间 | 成本 |
| :--- | :--- | :--- | :--- | :--- |
| **Unit Test** | 函数正确性 | 数万 | 分钟级 | 极低 |
| **Module Test** | 模块功能和性能 | 数千 | 小时级 | 低 |
| **Integration Test** | 模块间接口一致性 | 数百 | 小时级 | 中 |
| **SIL** | 软件栈完整功能 | 百万级 | 天级 (并行) | 中 |
| **HIL** | 硬件时序和资源 | 数万 | 天级 | 高 |
| **VIL** | 真车动力学响应 | 数千 | 周级 | 很高 |
| **Field Test** | 真实世界表现 | 百万公里 | 月级 | 极高 |

表中"典型覆盖场景数"为**示例口径**，用于表达各层级的相对量级，不是验收标准。

> [!TIP]
> **仿真测试是自动驾驶安全验证的基石**
>
> RAND Corporation 2016 年的经典估算指出：要以 95% 置信度证明自动驾驶的致死率比人类低 20%，所需实车里程在**百亿英里量级**（常被引用为约 10⁹–10¹⁰ 英里，具体数字随基线事故率、置信度与"允许观测到几次失效"的假设而变，原始口径**需核实**）——按现有车队规模要跑几十年到上百年。这个结论的方向是稳的：**纯里程堆叠在统计上不可行**。
>
> 因此行业转向两条路：
>
> - **仿真放大**：SIL/HIL 用并行把"里程"换成"算力"，一天跑完实车数年的场景量；
> - **加速评估 (accelerated evaluation)**：不再均匀采样，而是用重要性采样、场景参数优化、对抗搜索把采样密度集中到"最可能失效"的区域，用数量级更少的试验得到同等统计效力——本质上是把 §5.1 的 Area 3 搜索问题变成一个优化问题。
>
> 两条路都押在同一个前提上：**仿真保真度 (Fidelity)**——仿真中通过的场景在真实世界中也必须通过。而保真度本身无法用仿真证明（那是循环论证），只能靠"仿真-实车对照实验"标定：同一批场景在仿真与实车上各跑一遍，比对结果分布的差异。这是仿真验证方法论里最容易被跳过、也最致命的一环。

> [!NOTE]
> **闭环 vs 开环：端到端时代验证有效性的分水岭**
>
> - **开环评测**：用录制数据回放，比较模型输出轨迹与人类轨迹的距离（L2 误差/ADE）。它便宜、可复现，但**环境不会因模型的动作而改变**——模型偏了一步，后续场景仍是"人类开出来的"，错误的累积效应被掩盖。
> - **闭环评测**：模型输出真正驱动车辆，其他交通参与者随之反应。只有闭环才能暴露"一步偏、步步偏"的级联失败。
>
> 2025 起学术与工业界已基本形成共识：**开环指标不能作为安全放行依据**。开环指标为何会被平凡解刷高（ego-status 捷径）、以及闭环评测的具体做法，见 [BEV 感知与端到端 §6.3](perception.html)。对安全论证的直接含义是：§5.5 的"统计证据"必须以**闭环场景化仿真 + 实车**为主，开环指标只能作为开发期的快速回归信号。

### 5.5 端到端 / VLM 模型的安全论证

传统 pipeline 可以逐模块分解验证，端到端 / VLM 模型切断了这条路——输入到输出之间没有可独立验证的中间接口，生成式模型的行为也无法穷举。行业目前的务实策略不是"证明模型永远正确"，而是**四层证据的组合**：

1. **分层兜底 (containment)**：把模型当 QM 组件，输出由 ASIL 等级的安全监控器/安全包络把关（§4.3、§4.4、§4.5）——"模型可以错，但错误到不了执行器"；
2. **ODD 限定与降级**：明确运行设计域，边界条件（暴雨、超出区域、传感器退化）下受控降级或退出，压缩 SOTIF 的 Area 2/3（§5.1）；
3. **统计证据**：闭环场景化仿真 + 影子模式 + 数据飞轮（见 [BEV 感知与端到端](perception.html)）提供大规模行为证据，用"统计置信"替代"模块级证明"；
4. **结构化 Safety Case**：把上述证据组织成可审计的论证结构（如面向自主产品的 **UL 4600** 安全案例方法），AI 组件的开发过程参考 ISO/PAS 8800 的指南。

**面对"黑盒难题"，行业实际走的是三条路，且只有一条被证明可靠**：

| 路线 | 做法 | 评价 |
| :--- | :--- | :--- |
| **不解释，只兜底** | 放弃理解模型内部，用外部包络与监控限制其后果 | ✅ 当前唯一可认证的路线——安全论证的对象是"笼子"，不是"模型" |
| **事后解释 (post-hoc)** | 用 CoT、注意力可视化、显著图说明"模型为什么这么决策" | ❌ 不可作为安全证据（§1.2 CAUTION：叙述不保证忠实） |
| **结构化中间表示** | 把输出约束到可验证的动作空间/轨迹，用规则层逐条校验 | ✅ 与第一条配合使用，是 §4.5 契约层+可行性层的工程实现 |

这套组合里有三个容易被高估的证据来源，必须说清其效力边界：

- **影子模式 (shadow mode) 证明的是"不会更差"，不是"能开好"**：影子模式下模型只输出不执行，车辆仍由人驾驶——环境不会因模型的决策而改变，模型永远看不到"自己开下去会发生什么"。它能高效挖掘"模型与人类决策显著分歧"的样本（用于搜索 Area 3），但**不能替代闭环验证**：分歧样本里既有模型的错也有人类的错，而模型自己开时的错误累积效应在开环里根本不存在（§5.4）。
- **仿真闭环的有效性受限于仿真器的"反应真实性"**：闭环里其他交通参与者要对自车动作做出反应，而这个反应模型本身也是仿真的。如果 NPC 行为过于"礼貌"，闭环通过率会系统性偏高——这是把仿真结论外推到实车时最需要标定的一项。
- **模型每次更新都让已有证据部分失效**：端到端/VLA 的行为由权重决定，一次 OTA（哪怕只是数据配比调整）就可能改变长尾行为。因此安全论证必须**绑定到版本三元组：模型权重版本 + 训练数据版本 + 评测集版本**，任何一项变更都要走变更影响分析与回归验证，并纳入 R156/SUMS 的软件更新管理（§3.2）。这也是"持续学习"在安全上最难的地方：**它让 Safety Case 从一份文档变成一个必须持续维护的过程**。

一句话：**端到端 / VLM 的安全不是被"证明"出来的，而是被"兜住 + 验证 + 论证"出来的**——这也解释了 §1.2 的结论：当前 VLM 的务实定位是辅助决策系统，而非主控。

### 5.6 型式认证与准入：安全论证的出口

前面的 Safety Case 是"给谁看的"？除了内部评审与第三方认证，最终出口是**法规准入**。这里有一层常被忽略的关系：**ISO 26262 与 ISO 21448 都是自愿性标准，本身不是法律**——它们被法规引用后才具备强制力。理解这一点，才能判断"做到 ASIL D"到底意味着什么。

| 层级 | 代表法规/标准 | 管什么 | 与安全论证的关系 |
| :--- | :--- | :--- | :--- |
| **分级定义** | SAE J3016（L0–L5）、中国 GB/T 40429-2021《汽车驾驶自动化分级》 | 定义"谁是驾驶主体"、驾驶员是否必须在环 | 决定适用哪套准入法规与责任框架（§2.3） |
| **L2 组合辅助** | UNECE R79（转向设备，含 ACSF 自动转向功能）、**UNECE R171（2024，DCAS 驾驶控制辅助系统）** | 系统边界、驾驶员监控、脱手检测、越界告警 | L2 的责任主体是驾驶员，法规重点是"别让用户误用" |
| **L3 有条件自动驾驶** | **UNECE R157（ALKS 自动车道保持系统）** | ODD 限定（车道/速度/天气）、DSSAD 数据记录、接管请求时序、最小风险机动 | 首个真正允许"系统作为驾驶主体"的型式认证法规 |
| **L4 及以上** | 各国试点/许可制（无统一全球法规） | 运营许可、地理围栏、远程协助、安全报告 | 以"案例审批 + 运营监管"替代"型式认证" |
| **中国准入** | 四部委智能网联汽车准入和上路通行试点（2023 年启动、2024 年公布首批试点联合体）及相关强制性国标 | L3/L4 产品准入与上路通行 | 试点期内"企业主体责任 + 政府监管"并行（批次与时点**需核实**） |

> [!NOTE]
> **R157 是理解"L3 为什么难"的最好样本**
>
> R157 对 ALKS 的要求把前面几章的概念全部串了起来：**ODD 必须显式声明**（§5.1 压缩 Area 2 的手段）、**接管请求必须有明确时序，且驾驶员未响应时系统要自主完成 MRM**（§4.4 的 fail-operational）、**必须装 DSSAD 记录系统状态与接管事件**（事故归因与数据飞轮的合规来源，对应 §3.2 的 GB 44497）、**必须通过一系列标准化场景测试**（§5.3）。它也是"法规如何倒逼安全论证"的范例：不规定"你用什么算法"，只规定"你必须证明什么、记录什么、在什么条件下退出"。
>
> 对 VLA/端到端方案，这套框架既是约束也是出路——**法规不关心你的模型是不是黑盒，只关心 ODD 是否清晰、退出是否可靠、记录是否完整、统计证据是否充分**。这正是 §5.5 四层证据结构的合规映射，也解释了为什么"端到端难认证"更准确的说法是"端到端难以用传统模块级方法认证"，而不是"无法合规"。
